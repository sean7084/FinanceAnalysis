## 1. 一句话结论

**不换 RULE。** LightGBM 的漂亮数字是内样本拟合，注册表里同一个工件自己的 `deployment_note`
记录了它在真 holdout 上三配置全输；LSTM 是本轮唯一可裁决的 ML 臂，它按预登记判据**未通过**。
没有任何 `ETF_*` `ModelVersion` 被激活。

## 2. 方法与口径

| 项 | 取值 |
| :--- | :--- |
| 切分 | 6 个连续块，每折 hold out 2 块 → C(6,2)=15 个切分，6 个互不相同的块 |
| purge | 1 session（label horizon） |
| embargo | 5 sessions（每个 held-out 块之后） |
| 审计 | `audit_combinatorial_folds` 全部 15 个切分通过 |
| 度量方式 | 每臂跑**一条连续曲线**，按块切片；块内 maxDD 以自己的起点为峰 |
| 块基数 | 每块收益以块前最后一个净值点为基，所以块首日的收益不被丢掉 |
| 持仓规则 | 四臂逐字段相同：`BIWEEKLY / mom120 / 绝对动量关 / equal / dedup on / cap 2 / max_swaps 2`；只有 p5 臂改 `max_positions` |

**这不是逐折重训的 CV。** 每个块用的是**同一个已训练好的工件**，所以"样本外"只对
*参数选择*成立，对*模型拟合*不成立——这正是第 3 节判定有效性的原因。

## 5. 预登记判据与裁决

判据在跑之前写死（见 spec `ETF_Rotation_Gap_Closure_task-017.md` 的 R1–R4），跑完不改。

### R1 — row 256 稳定性：只陈述，不判定
六块中位 Sharpe 0.1620，83.33% 为正，块 5 为负。**结论：参考配置在时间上高度不均匀**，
不据此改任何默认值。

### R2 — p3 vs p5：三项全胜才改默认
判据依次为 Sharpe 中位数 → 正收益块占比 → maxDD 中位数。

| 判据 | p3 | p5 | 胜方 |
| :--- | ---: | ---: | :--- |
| Sharpe 中位数 | 0.1620 | 0.2725 | p5 |
| 正收益块占比 | 83.33% | 66.67% | **p3** |
| maxDD 中位数 | 17.96% | 14.54% | p5 |

**裁决：默认值保持 3。** p5 未三项全胜。这条记录的价值不在"p3 更好"，而在
"更高的中位 Sharpe 是用一致性换来的"——只看中位数会把 p5 误读成升级。

### R3 — ML vs RULE：三项全满足才算 CV leg通过
判据：ML 的 Sharpe 中位数高于 RULE，**且**正收益块占比不低于 RULE，**且** maxDD 中位数
不高于 RULE + 2pp。

| 臂 | Sharpe 中位 | 正收益块 | maxDD 中位 | 判据结果 |
| :--- | ---: | ---: | ---: | :--- |
| RULE | 0.1620 | 83.33% | 17.96% | 基准 |
| LSTM | 0.1238 | 66.67% | 15.93% | Sharpe 负、一致性负、回撤胜 → **未通过** |
| LightGBM | 2.4839 | 100% | 7.56% | 全部内样本 → **不可裁决** |

**裁决：CV leg未通过。** 完整闸门还需要 10b 的前向证据（影子账本 ≥20 次调仓，需数月），
本轮不可能满足；因此即使 CV leg通过也不会激活，何况它没有通过。

## 6. 与注册表 holdout 记录的交叉印证（关键）

本轮的 CPCV 是在**已烧掉的 holdout 之外**做的第二次独立测量。把它和注册表里 ML 工件
自己的 `deployment_note`（当年在真 holdout 上跑出来的）并排看，结论一致：

| 工件 | holdout（2024-01-01..2026-10-20）实测 | 闸门 |
| :--- | :--- | :--- |
| LightGBM id 63（本轮钉住的就是它） | alpha **−0.0141 / −0.0026 / +0.0338** vs RULE **+0.1821 / +0.1757 / +0.1752**；holdout rank IC 仅 4/6 折为正，均值 0.0306 | 三配置**全败** |
| LSTM id 64（`2023-11-30-oos23`，非本轮钉住的 id 100） | alpha +0.1646 vs RULE +0.1821（#1 配置）；另两配置胜，但 beta 1.08–1.19 vs RULE 0.61–0.69、maxDD 0.41–0.42 vs 0.18–0.20 | 2/3 通过但不干净 → 不上线 |
| LSTM id 100（本轮钉住，Phase D row 209） | alpha 0.0888 vs 0.1821、maxDD 0.4567 vs 0.2000、beta 1.1038 vs 0.6070 | **FAIL** |
| ENSEMBLE id 65 | alpha +0.0641 / +0.0712 / +0.0355 vs RULE +0.1821 / +0.1757 / +0.1752 | 三配置**全败** |

**同一个 LightGBM 工件，在训练集内 Sharpe 2.48，在真 holdout 上 alpha −0.014。** 这两行数字
放在一起，就是"内样本分布不能当能力"的最直接证明，也是不能拿它替换 RULE 的理由。

### 6.1 顺带查出的一个缺陷（已修）

`rotation_engine._call_predictor` 原先只把 `['ts_code', *features]` 交给 predictor，丢掉了 `date`。
LSTM 的评分契约需要每行的 as-of 日期；缺了它会退回"最新 eligible 快照"，于是
**每一个历史 session 都拿到同一份分数向量**——整段回测实际上持有一个静态组合。
这解释了 Phase D row 209 的 beta 1.10 与 maxDD 0.46：那不是模型的风险特征，是"两年半不换仓"
的产物。

修复后 `date` 随帧传递（LightGBM 按训练列 reindex，数值逐位不变），本轮 LSTM 运行
**0 条** "no date column" 告警。**因此 row 209 的 LSTM 数字不应再被引用**；用修复后的代码
重测需要再查一次已关闭的 holdout，纪律不允许，故只记录失效、不补新数字。

## 11. 按折重训复赛（2026-10-25 晚，Phase 14-15）

§3-§6 的四臂读数有一个共同的弱点：ML 臂用的是**已训练工件**，其训练窗口覆盖被测块。本节改用 Phase 14 的按折重训：每个块由一个**从未见过该块**的模型评分。

### 11.1 方法

- 面板 `2016-01-29..2023-12-31`，6 块，`--cpcv-test-blocks 1`（每块恰好一个模型），窗口与 §4 可比。
- `run_etf_rotation_backtest --cpcv-retrain`：对每块用"其余块 + purge + embargo"训练一个折模型，只给该块打分与跑组合回测，然后丢弃——不注册、不落盘、不激活。
- **每块是独立运行、从初始资本起算**：一个块的模型只对该块有效，没有可切片的连续曲线。因此 RULE 基准也用同一模式重跑，否则比较会混用两种方法。
- 泄漏断言：任何训练日期落在自己块内即拒绝训练。

### 11.3 裁决（对照 §5 预登记的 R3'）

R3' 要求三条同时成立：Sharpe 中位数 > RULE、正收益块占比 ≥ RULE、maxDD 中位数 ≤ RULE + 2pp。

| 臂 | Sharpe | 一致性 | 回撤 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| LightGBM | 输（−0.0136 < 0.2227） | 输（50% < 83.33%） | **赢**（9.35% < 19.97%） | 不通过 |
| LSTM | 输（0.0249 < 0.2227） | 输（66.67% < 83.33%） | 赢（17.32% < 19.97%） | 不通过 |

**结论：不替换 RULE。** 两条 ML 臂在收益与一致性上都不敌 RULE，只在回撤上占优。这与 §6 的观察一致，也是本轮最诚实的一句话：**ML 的价值不在选股，在降低回撤**。§6 里 LSTM 六块 IC 全正而组合输给 RULE，原因现在更清楚——正的 rank IC 不足以抵消换手与选股集中度带来的收益损失。

**§3-§6 的 LightGBM 读数（Sharpe 中位数 2.4839）作废**：按折重训后是 −0.0136。两者差 2.5 个 Sharpe，就是"用见过答案的模型评分"的代价。

### 11.4 一个方法学发现：序列模型的 purge 必须覆盖窗口长度

首次 LSTM 重训被护栏拦下两次，两次都是真问题：

1. `--cpcv-embargo 5` 时，块后有 15 个训练日期的 20 日输入窗口会伸进块内 → "14 holdout dates appear inside training windows"。
2. 修正后仍触发"a training target date is not before the holdout start"——该断言原本只对 expanding 折成立，组合折合法地保留块后日期。

**规则**：对序列模型，embargo 必须 ≥ `sequence_length`。LightGBM 是逐行特征，`embargo=5` 足够；LSTM 用 `--cpcv-embargo 20`。这不是可调偏好，是有效性前提——不足时模型的输入里就有块内行情。表 11.2 的 LSTM 臂即用 20 跑出。

### 11.5 第四臂：RULE 选股 + LightGBM 否决（已测）

> **2026-10-25 更正**：本节（以及 §11.6）的 ML 数字是用 `purge=1` 跑出来的，而标签窗口是 20 个
> session——折模型在训练时看到了被测块的答案。修正后的读法见 **§12**，本节保留为"当时跑了什么"
> 的记录，其 ML 读数不得单独引用。

**假设**：ML 分数当**过滤器**有用，当**选择器**没用。§11.3 的两条臂都是"用 ML 排序"，输在收益与一致性、赢在回撤——这正是过滤器该有的形状。

**实现**：`--cpcv-retrain --cpcv-hybrid --model LIGHTGBM`。每块训练一个折模型（同 11.1），但**引擎的选择模型仍是 RULE**；折模型只把横截面里 ML 分数处于末位 20% 分位的候选剔除，再走 RULE 的选择约束。分位**固定 20%，全程不调**。

| 1 | 2016-01-29..2017-05-26 | 0.6654 | 0.8032 |
| 2 | 2017-05-31..2018-09-13 | 0.1688 | 0.2906 |
| 3 | 2018-09-14..2020-01-10 | 0.7487 | 0.9109 |
| 4 | 2020-01-13..2021-05-13 | 1.2287 | 1.3841 |
| 5 | 2021-05-14..2022-09-02 | −0.1436 | 0.0463 |
| 6 | 2022-09-05..2023-12-28 | 0.2227 | −0.3911 |

| 臂 | Sharpe 中位数 | 正收益块 | maxDD 中位数 | 区间收益中位数 | 最差块 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| RULE | 0.2227 | 83.33% | 17.97% | +3.03% | +3.03%（第 5 块 −7.76%） |
| **RULE + LGB 否决** | **0.2906** | **83.33%** | **15.62%** | **+3.27%** | **−8.78%** |

**结论：LightGBM 否决臂是唯一在三项 leg（criteria，与持仓 leg 同词、由上下文区分）上都不劣于 RULE 的 ML 臂。** 按预登记的新臂判据（"三项 leg中至少两条不劣、且 maxDD 不更差，即可进入前向对照"），它**通过**——Sharpe 与 maxDD 都更好，一致性持平。**但 §11.6 用 LSTM 换掉否决模型后结论反转**，所以这条通过不能单独作为证据。

**但必须同时说清两点**：

1. **尾部更差**。第 6 块 −8.78%，RULE 是 +3.03%。中位数改善是"少输在中间块"，不是"更抗尾部"。
2. **一个分位、一个配置、6 块**。这是稳定性读数，不是显著性检验；分位一旦开始调就又是一次搜索，本轮不动。

因此本轮的正确结论不是"换成混合臂"，而是**"RULE 保持生产，混合臂获得进入前向对照的资格"**。前向窗口（2026-10-25 起、≥20 次调仓）是它下一道门。

### 11.6 第四臂的对照：LSTM 否决（已测）

> **2026-10-25 更正**：同 §11.5，本节的 ML 数字受 `purge=1` 泄漏影响，修正后的读法见 **§12**。

同一套 `--cpcv-hybrid`，把否决模型换成 LSTM（`--cpcv-embargo 20`，见 §11.4）：

| 臂 | Sharpe 中位数 | 正收益块 | maxDD 中位数 | 区间收益中位数 | 最差块 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| RULE | 0.2227 | 83.33% | 17.97% | +3.03% | −7.76% |
| RULE + LGB 否决 | **0.2906** | 83.33% | **15.62%** | **+3.27%** | −8.78% |
| RULE + LSTM 否决 | 0.1515 | 83.33% | 17.99% | +1.37% | −22.61% |

**LSTM 否决不通过**：Sharpe 中位数低于 RULE（0.1515 < 0.2227），回撤持平，最差块 −22.61% 远差于 RULE 的 −7.76%。

**这改变了 §11.5 的读法。** 两个否决模型的结论相反，所以"ML 当过滤器有用"**不是**一个稳健发现，而是**LightGBM 特有的**一个观测。正确的表述是：

- LightGBM 否决臂通过了预登记的 CV 判据（Sharpe 与 maxDD 都更好、一致性持平）；
- LSTM 否决臂不通过；
- 因此"过滤器"假设**未获独立复现**。一个配置、一个分位、6 块、两个模型给出两种答案——这不足以支撑任何生产变更。

**结论不变且更强：RULE 保持生产。** 混合臂连"进入前向对照"的资格都只能算 50%：LGB 版本可作为候选观察，但在前向窗口累积 ≥20 次调仓前，不该有别的动作。若要让这个假设变得可判定，下一轮的正确做法是**固定分位、只换否决模型与面板起点**做敏感性检验，而不是继续在同一个 6 块上换参数。

### 11.7 边界

- 每块独立起算，与 §4 的连续曲线分布**不可直接比较**；同一张表内只比同方法读数。
- RULE/LightGBM 臂 `embargo=5`、LSTM 臂 `embargo=20`；块边界相同，训练集不同。
- 6 块、单一面板；这是稳定性读数，不是显著性检验。
- 面板止于 2023-12-31，**未使用释放后的 2024-2026**（那会改变块边界，使本节与 §4 无法对照）。释放后的读数属下一轮，且只能叫调优数字。

## 12. 更正：purge 必须等于标签窗口（2026-10-25）

### 12.1 问题

`run_etf_rotation_backtest` 原先把 CPCV 的 purge 硬编码为 **1 个 session**，注释写着"RULE 不拟合标签，1 个足够；拟合模型应当用自己的 horizon"。但标签窗口是 `ETF_LABEL_HORIZON_DAYS = 20`：块起点前 19 个交易日的训练样本，其 `fwd_return` 是用**块内行情**算出来的。折模型在这一段上训练，等于看过被测块的答案。

方向上是**抬高** ML 成绩，所以 §11 里两个选择臂"输"的结论安全；但 §11.5 那个唯一"通过"的 LightGBM 否决臂（0.2906）是被污染的。

同时发现第二个问题：`combinatorial_purged_folds` 用 `horizon_days` 同时截断面板尾部（标签必须已实现），所以**改变 purge 会连带改变块边界**。RULE（purge=1）与 ML 臂（purge=20）因此落在不同的划分上，中位数不可直接比较。

### 12.2 修正

- `resolve_cpcv_purge(model_type, requested, label_horizon)`：RULE 保持 1，ML 臂默认 `ETF_LABEL_HORIZON_DAYS`；`--cpcv-purge` 只能调高，调低直接 `CommandError`（不是警告）。
- `combinatorial_purged_folds(..., panel_tail_days=...)`：**布局只由标签窗口决定**，purge 只影响训练集。RULE 与 ML 臂现在落在同一批块上。
- 证据台账（`apps/etf_rotation/evidence.py`）记录每次测量的上下文与结果，重复读取同一上下文会被计数。

### 12.3 重测（同一批块，六个，2016-01-29..2023-12-01/29）

| 臂 | Sharpe 中位数 | 正收益块 | maxDD 中位数 | 区间收益中位数 | 最差块 |

| **RULE + LGB 否决**（purge=20） | **0.5400** | 83.33% | **16.78%** | +6.96% | −17.62% |

### 12.4 结论

1. **两个选择臂仍然失败**，且 LightGBM 更差（−0.1041 vs §11 的 −0.0136）。修正泄漏没有救活它们——这与"容量不是瓶颈"的判断一致。
2. **LightGBM 否决臂在正确 purge 下仍然通过，而且更强**（0.2906 → 0.5400）。这说明之前的泄漏**反而在伤害**它：块内答案让模型把"将来会涨"的名字排在前面，而否决只砍末位 20%——模型越会认赢家，被砍掉的越是随机名字，过滤效果越差。这个方向性解释必须保守看待（它是事后推理），但数字本身是可复现的。
3. **LSTM 否决臂仍然不通过**（0.0841 < 0.1881）。两个否决模型结论依旧相反，**"ML 当过滤器"未获独立复现**。
4. **两个否决臂的尾部都显著更差**：LGB −17.62%、LSTM −21.93%，RULE −6.31%。中位数改善是以更差的坏年份换来的。
5. 因此生产结论不变：**RULE 保持生产**，LGB 否决臂只能作为前向观察候选，且必须先过计划 §9 收紧后的闸门（≥2 个否决模型或 ≥2 个面板起点上复现）。

### 12.5 边界

- 六个块、单一面板；这是稳定性读数，不是显著性检验。
- LSTM 臂 `embargo=20`（序列窗口 20 日），其余 `embargo=5`；块边界相同，训练集不同。
- §11 保留为历史记录，其 ML 读数不再单独引用；本节的表取代它作为当前读数。

**LGB 否决臂也不再有资格进入前向观察**（计划 §9 的 1a 条款要求 ≥2 个否决模型或 ≥2 个面板起点同时通过；它只有 2/3 个起点、1/2 个模型）。

## 14. 指数估值特征族：基础设施建成，特征族就地终止（2026-10-25）

### 14.1 做了什么

- `ETFIndexMapping`（迁移 0013）+ `build_etf_index_mapping`：用 `fund_basic` 的 `benchmark` 文本匹配 `index_basic` 目录（9,575 个指数名），最长名称优先，复合基准记 `partial`。结果：可选池 1,715 个名字中 **1,474 个已映射（85.9%）**，高于预登记的 70% 门槛。报告：`docs/reports/etf-index-mapping-coverage.md`。
- `IndexValuationDaily`（迁移 0014）+ `sync_index_valuation`：按已映射指数逐个拉 `index_dailybasic`。
- `attach_index_valuation` + 四个列（迁移 0015）：PE/PB 的 3 年分位、换手 z-score、`has_index_valuation` 覆盖标记；一律按 **D-1** 滞后（该接口收盘后发布）。

### 14.2 终止理由：数据源覆盖不足

`index_dailybasic` **只覆盖 6 个宽基指数**（上证指数、上证50、深证成指、沪深300、中证500、创业板50）。298 个已映射指数里 292 个返回空帧——不是限速：`000002.SH` 这类明确存在的指数在 MCP 直连下同样返回空，说明是该接口的覆盖范围，不是调用问题。

由此，可选池中只有 **207 / 1,715（12.1%）** 的名字能拿到估值特征，远低于预登记的 70% 门槛。

**按计划处置：特征族就地终止，不做替代性造数。** 四个列保留在模型上（值为 NULL）、`attach_index_valuation` 保留，但**不进入 `FEATURE_COLUMNS`**。理由：一个 88% 缺失的特征，模型学到的是"这个基金有没有宽基映射"，而不是估值信号——那会把覆盖偏差伪装成 alpha，正是计划 §10 第 4 条点名的风险。

保留的基础设施并非白做：映射表（85.9%）可直接用于 P30 的成分广度/离散度（那需要 `index_weight` + 成分行情，不依赖 `index_dailybasic`）；估值列只需在有真实覆盖的数据源到位时移回 `FEATURE_COLUMNS` 一行。

### 14.3 边界

- 6 个宽基指数的估值数据是完整的（2015-01-05..2026-10-23，共 17,168 行），可以作为宽基 ETF 的辅助变量单独研究，但不能作为全池特征。
- 该结论只针对 TuShare `index_dailybasic`；换成中证官网或 Wind 的指数估值表可能解决覆盖问题，但那属于新的数据源决策。

## 15. 滚动 vs 扩窗：训练窗口形状是被忽视的变量（2026-10-25）

`--fold-plan expanding` 新增后，两种计划共享同一批验证块（首个验证块都在 750 个 session 之后开始），
唯一差别是训练窗口——expanding 只增长，rolling 固定 750 日滑动。面板 2016-01-29..2023-12-29，6 折。

| 折计划 | 臂 | Sharpe 中位数 | 正收益块 | maxDD 中位数 | 收益中位数 |
| :--- | :--- | ---: | ---: | ---: | ---: |
| expanding | RULE | 0.0791 | 66.67% | 19.24% | −0.38% |
| rolling | RULE | **0.0791** | **66.67%** | **19.24%** | **−0.38%** |
| expanding | LightGBM 选择 | −0.7320 | 50.00% | 18.79% | −14.17% |
| rolling | LightGBM 选择 | **+0.4945** | 66.67% | **14.24%** | **+4.10%** |

两件事：

1. **RULE 在两个计划上逐位相同**——它不拟合，训练窗口形状对它是空操作。这不是巧合而是对照有效的证据：两个计划确实共用同一批验证块。
2. **LightGBM 选择器差了一个 Sharpe 量级**：expanding −0.7320，rolling +0.4945。固定窗口让它从"大幅落后 RULE"变成"三条 leg 全胜"。

**解释（要当作假设，不是结论）**：expanding 让 2016-2017 的行情永久留在训练集里，而 ETF 的横截面关系在 2021-2022 之后明显变了（报告 §11.2 的逐块 IC：0.1011 / 0.0903 / 0.0696 / −0.0051 / 0.0223 / 0.1109，中段塌陷）。rolling 把这段陈旧历史切掉，模型就在中段少输。这与"concept drift 而不是容量不足"的判断一致。

**这是单一面板起点的读数，按计划 §9 的 1a 条款不能作为行动依据。** 已按预登记格栅复核（`docs/reports/preregistration/sensitivity-rolling-selector-2026-10-25.md`，3 个起点，3/3 才算复现），结果见 §16。

**一个方法学后果**：在此之前所有 ML 臂的失败都是在 expanding 下测的（§11、§12）。如果滚动复现，那些结论要重新表述为"expanding 下的失败"，而不是"ML 不行的证据"。这正是计划把 P33 放在 P35（模型家族决策门）之前的理由。

## 16. 滚动选择器的预登记复核：1/3，未复现（2026-10-25）

预登记 `docs/reports/preregistration/sensitivity-rolling-selector-2026-10-25.md`（哈希 `a9cc138a3ea7`），
3 个面板起点，两种臂都用 rolling 计划：

| 臂 | 2016-01-29 | 2017-01-03 | 2018-01-02 | 复现 |
| :--- | :--- | :--- | :--- | :--- |
| `rule-rolling` | 0.0791 / 66.7% / 19.24% | 0.4460 / 83.3% / 13.26% | −0.5284 / 16.7% / 11.58% | — |
| `lgb-select-rolling` | **0.4945** ✓ | 0.0301 ✗ | 0.2736 ✗（回撤输） | **1/3** |

**结论：未复现。** §15 里那个 +0.4945 和 §12 里那个 0.5400 是同一类东西：**单一面板起点上的边界产物**。滚动窗口确实让 LightGBM 在 2016 起点上从 −0.73 变成 +0.49，但在 2017 起点它输给 RULE，在 2018 起点赢 Sharpe 却输回撤。

### 16.1 一个比任何臂都重要的发现：测量仪器比效应更吵

RULE 自己在三个起点上的 Sharpe 中位数是 **0.0791 / 0.4460 / −0.5284**。RULE 没有任何可学习参数、没有任何随机性——它的读数波动**全部**来自"块怎么切"。2017 起点每块约 195 个 session（≈19 次双周调仓），2016 起点每块约 200 个，2018 起点同样。

也就是说：**6 块 × 约 20 次调仓的分布，其起点间波动（约 1 个 Sharpe）大于我们试图检测的效应（0.1-0.5 个 Sharpe）。** 在这个信噪比下，任何"某臂在某个起点上赢了"的结论都不可靠，无论它看起来多显著。

这解释了本轮**所有**看似矛盾的结果，也把结论从"哪个臂更好"改写成："用当前的测量仪器，我们无法判定哪个臂更好。"

**因此 P35（模型家族决策门）的答案不是"不加模型"，而是"在仪器改进之前，任何加法都不可判定"。** 具体要改的是块内调仓次数与块数（见 §17）。

### 18.2 启用时发现的问题

把四个列接入 `FEATURE_COLUMNS` 后，全量重算在 upsert 阶段失败：

```
HINT: Ensure that no rows proposed for insertion within the same command have
duplicate constrained values.
```

即**装配出的 block 里存在重复的 (etf, date) 行**。这不是份额流引入的——它是既有缺陷，只是此前没有触发。诊断过程中还发现并修掉了两个同类的"多对多合并"缺陷：

- `attach_index_valuation` 与 `attach_share_flow` 都会把多条历史行映射到同一个 session（块的 session 列表是稀疏的），未去重时 merge 是**笛卡尔积**。两处现在都 `drop_duplicates(keep='last')` + `validate` + 长度守卫。
- 一个 2 行的测试块在修复前会返回 2,000 行——这类缺陷在小样本上完全看不出来，所以现在有一条专门的回归测试（`test_one_row_per_fund_per_session`）。

**块内重复键本身仍未定位**：它在加特征之前就存在，用 `validate='one_to_one'` 的形状报错。因此四个列**暂时不接入** `FEATURE_COLUMNS`，管线恢复可用；`attach_share_flow` 与其测试保留，修好重复键后只需把四个名字移回元组。

### 18.3 边界与下一步

- 份额流是本轮唯一一个**数据覆盖 100%** 的新特征族，值得在重复键修好后立即测一次；它的 `flow_x_mom` 交互是本轮设计里最有依据的一个（ETF 申赎流与动量的组合在文献里有稳定证据）。
- 重复键问题的定位方法：对 `_iter_chunk_blocks` 的输出按 `(etf_id, date)` 做 `duplicated()` 并打印前若干例，先判断是 master/panel 侧还是合并侧引入。
- 在该缺陷修复之前，**任何新增特征列都不能启用**——这是本轮的第四个"先修尺子再量东西"的实例（前三个：purge、块边界、仪器分辨率）。

### 19.1 先更正 §18 的一个误判

§18 把"upsert 拒绝重复键"归因于装配块的既有缺陷。**那个判断是错的**：真正原因是我在一次回填还没结束时又启动了第二次，两个进程写同一批 (etf, date)。单进程重跑全量后通过——2,602,300 行、`has_share_flow` 803,310 行、**eligible 覆盖 345,567/360,701 = 95.8%**。

- `attach_index_valuation` 原来用 `{index_code: etf}` 反查，**同一指数下的 170 只 ETF 只有一只拿到估值**；现在改为先映射 ETF→指数再 join（新增测试 `ValuationSharesAnIndexTests`）。

## 20. 宏观 regime 闸门（P32）：按设计工作，但不是选择器（2026-10-25）

### 20.1 实现

宏观**不进排序模型**，只做组合层的曝光闸门——这是计划 §10 第 5 条的硬约束，有测试强制（`test_macro_series_never_become_a_ranking_feature`）。

- `BacktestConfig.macro_gate_pmi`（0 = 关闭，默认关闭 → 旧运行逐位不变）+ `macro_gate_scale`（默认 0.5）。
- `macro_risk_gate(config, session)`：取 **发布日 35 天之后**才开始可用（月度指标次月发布，保守取值），PMI 低于阈值时把 `exposure_scale` 乘以 `macro_gate_scale`；与 Kelly governor 相乘而非相加。
- CLI `--macro-gate-pmi` / `--macro-gate-scale`；`state.macro_history` 记录每次开闸的日期与 PMI 值，进报告。

### 20.2 结果（RULE，同一批块）

| 指标 | 无闸门 | PMI<50 → 0.5 倍 |
| :--- | ---: | ---: |
| Sharpe 中位数 | 0.1881 | 0.1283 |
| 正收益块 | 83.33% | **100.00%** |
| maxDD 中位数 | 17.97% | **16.95%** |
| 收益中位数 | +1.85% | +0.98% |
| **最差块** | −6.31% | **−3.21%** |

**闸门做的事和它该做的一致**：最差块腰斩、全部六块转正、回撤略降；代价是中位 Sharpe 与收益下降。

### 20.3 判定

按 R3' 的三条 leg，它**不通过**（Sharpe 与收益都更低）——但这个判定本身是错位的：闸门是**风险控制**，不是收益增强，用"Sharpe 中位数更高"去要求一个减仓开关，等于要求保险不花保费。

正确的问题应该是："用 0.18 的 Sharpe 换 −6.31% → −3.21% 的尾部，值不值？" 这取决于资金约束与回撤容忍度，是**偏好问题而非可测量问题**。诚实记录：闸门按设计工作，是否采纳需要用户的风险偏好输入，本轮不做裁决。

**边界**：6 块、单一面板起点、单一阈值（50）。按 §16.1 的噪声尺度，0.06 的 Sharpe 差在噪声带内，所以连"代价多大"都只能说个量级。

### 20.4 这一阶段的通用结论

三个特征族（指数估值、份额流、宏观）走完，得到三种不同的"不行"：

| 特征族 | 数据 | 结果 | 结论类型 |
| :--- | :--- | :--- | :--- |
| 指数估值 | 12.1% 覆盖 | 未启用 | **数据源不可得**（换源可解） |
| 份额流 | 95.8% 覆盖 | 两臂都降 | **测不出增量**（仪器限制） |
| 宏观 | 100% 覆盖 | 按设计工作 | **不是选择器，是风控开关**（偏好问题） |

三者都不是"特征工程没做好"，而是三种不同的边界。**下一个值得投入的动作仍然是 §17.2 的仪器改造**——在此之前，第四、第五个特征族只会得到同样的结论。

## 22. 消融协议（P26）

规则只有一条：**一次只改一样**。折计划、purge/embargo、判据、分位全部固定；每行结果必须带证据台账 id 与预登记哈希。命令级强制已经有了两处：

- `run_etf_rotation_backtest --cpcv-retrain` 每次测量都写台账，并在输出里说明"这个上下文此前被测过几次"；重复测量不会静默通过。
- `measure_etf_rotation_sensitivity` 拒绝任何未在预登记文件里声明的单元格（`--preregistration` 必填且哈希入档）。

标签维度的消融已完成（§13.2：`rank_pct` vs `dd_rank`，同折同分位）。特征维度做了两轮（§19 份额流、§23 成分广度），折计划维度做了 §15 与 §16。汇总是 §17.1 的矩阵，每一行都能回指一个证据台账条目。

## 23. 成分广度：数据层建成，覆盖率把它挡在模型之外（P30）

### 23.1 数据层

- `IndexWeightSnapshot`（迁移 0019）+ `sync_index_weight`。`index_weight` 返回**有上限的一页**（实测 7,000 行），一个宽基指数单月就有上千个成分，所以命令把"满页"当作截断信号：窗口一分为二重取，直到每片低于上限；单月仍满页则明确报错而不是悄悄丢月份。
- 同步按"被多少只合格 ETF 跟踪"降序进行，中途停下也保证覆盖最大化。本轮同步了 **116 个指数 / 2,971,264 行**后停止（`--only-missing` 可续跑）。
- `features.attach_index_breadth` 用 `markets.OHLCV` 计算三个特征，**所有输入取 D-1**（价格本身也 shift，否则 D 自己的收盘会泄漏进 D 的广度）：
  `idx_share_above_ma60`（成分中站上 60 日均线的权重占比）、`idx_ret_dispersion_20d`（成分 20 日收益的加权横截面标准差）、`idx_mom_consistency`（与指数方向一致的权重占比）。
  少于指数一半权重可定价的 session 记 NaN，并写 `has_index_breadth=0`。

### 23.2 覆盖率：53%，低于 70% 门槛

按 eligible 行统计（不是按 ETF 只数）：

| 区间 | eligible 行 | 有广度 | 覆盖率 |
| :--- | ---: | ---: | ---: |
| 全样本 | 360,701 | 192,004 | **53.2%** |
| 测量窗口 2016-2023 | 144,164 | 76,600 | **53.1%** |

逐年：2016 9.6% / 2017 9.3% / 2018 21.9% / 2019 36.0% / 2020 52.9% / 2021 63.6% / 2022 62.6% / 2023 60.0% / 2024 54.1% / 2025 53.4% / 2026 52.6%。

## 25. 算力（P21）：线程数买时间，但不改读数

同一个 `lgb-select` 臂、同一批块（2016-01-29..2023-12-31，6 blocks，purge=20，embargo=5），只改 `ETF_LGB_NUM_THREADS`：

| 线程 | wall-clock | 逐块 Sharpe / IC | 结论 |
| :--- | ---: | :--- | :--- |
| 4（旧硬编码值） | 92.3 s | 0.2889/0.1523, −0.7311/0.0364, 0.5948/0.0283, 0.2829/0.0111, −0.4506/−0.0263, −0.3607/0.0005 | 基线 |
| 14（新默认 `min(16, cpu-2)`） | **66.8 s** | **逐位相同** | **1.38× 加速，读数不变** |

只快 38%，因为一次测量里训练只占一部分——数据装配（面板读取、purge、特征组装）是固定成本。这也说明"算力不是瓶颈"（§17.2）：把线程从 4 提到 14 买到的只是等待时间，不是可判定的效应。

另外两项：

- **可复现性有断言测试**：同一 seed 下两次 `lgb.train` 的分数逐位相同（`LightgbmSeedReproducibilityTests`，`num_threads=1` + `deterministic`）；上面的 4/14 线程对照则说明"线程数不同、结果到小数点后四位仍一致"。
- **GPU 探测**：当前 wheel 与宿主无 OpenCL 设备，`device=gpu` 直接报错，因此停在 CPU；`NATIVE_PARAM_NAMES` 保留了 `device/device_type/gpu_use_dp`，换一台有 OpenCL 的机器只需要设 `ETF_LGB_PARAMS`，不需要改代码。LSTM 的八个容量参数现在由 `ETF_LSTM_*` 决定，默认值与原字面量一致。

顺带的一次管线验证：这次 28 列特征的重跑与 §19.2 的逐块 IC（0.1523/0.0364/0.0283/0.0111/−0.0263/0.0005）和 Sharpe 中位数（−0.3607）**完全一致**，说明 P30 的改动没有扰动既有特征路径。

## 26. 可追溯性修正（2026-10-26）：没有读数变化

这一节不产生新数字，只记录把"先登记后运行、每次读取可见"从纪律变成机制所补的四处接线，
以及因此**变得可见**的两件事。

**修了什么。**

1. `previous_book` 现在按 arm 取上一本书。此前它只按 `signal_type` 取最新信号，两个影子臂同日

3. 台账上下文补上了执行模型——费率、band、容量、Kelly、宏观闸门、选择旋钮，全部经

4. `--fold-plan` 在 walk-forward 路径也生效（`expanding`/`rolling`；`cpcv` 被拒绝，逐折选

**因此变得可见的两件事。**

- §17.1 拆成按特征 schema 分开的两张表，每行带台账 id 与预登记哈希。`cpcv/LGB 选择`

## 28. 标签补齐与消融透视（2026-10-27，P24/P26 / #71）

**新增第四个标签：`label_downside_rank`。** 与 `label_dd_rank` 同一方向（池内最安全 = 1.0），但由
`fwd_downside_deviation` 而不是最大回撤构建，因此回归目标与排序目标不再共用同一个序列。

## 30. 运行时锁定（2026-10-27，#13）

`requirements/base.txt` 里九个包本来就是**精确锁版本**的（lightgbm 4.6.0 / torch 2.12.0 /
scikit-learn 1.8.0 / numpy 2.4.6 / mlflow 3.12.0 / akshare 1.18.63 / tushare 1.4.29 /
TA-Lib 0.6.8 / django-celery-beat 2.9.0），所以 #13 的剩余工作不是"去锁"，而是**让锁定可验证、
让工件记得自己是谁产的**：

- `library_versions()` 写进 LightGBM 与 LSTM 工件 metadata，也写进每条台账行的上下文。
- `PinnedRuntimeTests` 把 `requirements/base.txt` 的 pin 与 venv 的实测版本逐项比对，不一致
  就失败——重建后的环境若漂移，测试先叫，而不是等某个读数对不上再猜。
- 加速器如实记录（`docs/reference/ml-runtime.md`）：LightGBM wheel 无 OpenCL，GPU 关闭；
  本 WSL2 venv 的 torch **可用 CUDA**（`torch.cuda.is_available()` 为 true，
  `torch.version.cuda` = 13.0），LSTM 可走 GPU。任何计时结论旁边都应注明加速器：同一配置的
  CPU 与 CUDA 运行不是可互换的证据。
